# work

새 개발 작업이 시작될 때마다 그 작업만의 작은 설계를 만들고 정리하는 공간이다. 전체 설계가 아니다. 전체 설계는 `docs/design/`에 있다.

## 용도

- 작업 브랜치 하나에 대한 작은 설계와 진행 기록
- 여기에 두지 않는 것: 전체 설계·설계 변경(`docs/design/`), PR 설명(`docs/PR/`), 조사 보고서(`docs/report/`)

## 이름 규칙

```
docs/work/{브랜치 이름}/MMDD_{문서-이름}.md
```

- 브랜치 이름의 슬래시는 하위 폴더가 된다. 문서가 브랜치별로 정리된다.
  - 브랜치 `feat/double-tap-selection` → `docs/work/feat/double-tap-selection/1102_double-tap-selection.md`
- 식별자는 쓰지 않는다. 브랜치 폴더가 식별자 역할을 한다.
- `MMDD`는 한국 시간 작성일, `{문서-이름}`은 소문자 영문 kebab-case 권장(한글 허용, 공백 금지).
- 한 브랜치에 문서가 여러 개 필요하면 같은 폴더에 둔다. 첫 문서가 그 작업의 주 문서다.

## 작성 규칙

- **새 브랜치에서는 코드를 쓰기 전에 이 문서부터 만들어 커밋한다.** (커밋 순서 1번)
- 작업하면서 「진행 기록」과 상태를 갱신한다. PR을 Ready for review로 바꾸기 전에 진행 기록이 최신이어야 한다.
- 병합 뒤 상태를 「완료」로 바꾸는 일은 **다음 작업 브랜치에서** 한다. (병합된 브랜치에는 더 커밋하지 않는다)
- 상위 설계와 다르게 구현해야 하면 먼저 `docs/design/`에 변경 설계서를 쓰고 합의를 받는다. 그 변경 설계서는 해당 항목에 한해 기존 설계보다 우선한다. (`docs/design/README.md`)
- 「목표」는 확인 가능한 문장으로 쓴다. (나쁨: 「선택을 잘 되게 한다」 / 좋음: 「두 줄에 걸친 문장을 더블탭하면 두 줄이 모두 선택된다」)
- 상태 값: `계획` / `진행 중` / `리뷰 중` / `완료` / `중단`

## 문서 양식

아래를 그대로 복사해 쓴다. 해당 없는 절은 지우지 말고 「해당 없음」이라고 쓴다.

```markdown

| 항목 | 내용 |
|------|------|
| 작성일 | YYYY-MM-DD |
| 작성자 | {GitHub ID} |
| 브랜치 | `{type}/{작업-이름}` |
| 기준 커밋 | `{dev의 짧은 해시 7자리}` |
| 상태 | {계획/진행 중/리뷰 중/완료/중단} |
| 관련 PR | PR{번호} (`docs/PR/…`) 또는 「PR 전」 |

## 1. 지금 작업 내용

{무엇을 왜 하는지 한두 문단}

- [ ] {확인 가능한 문장}
```
