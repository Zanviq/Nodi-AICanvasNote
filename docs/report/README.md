# report

사용자가 보고서를 요청하면 조사하고 그 내용을 출처와 함께 정리해 두는 공간이다. 테스트 데이터와 테스트 계정 문서도 여기에 둔다.

## 용도

- 조사 보고서 (기술 조사, 비교, 실험 결과, 특정 PR 분석 등)
- 테스트 데이터·계정 문서 (테스트 데이터나 계정을 만든 단계 뒤에 반드시 작성)
- 여기에 두지 않는 것: 설계(`docs/design/`), 작업 설계(`docs/work/`), PR 설명(`docs/PR/`)

## 이름 규칙

- 형식: `MMDD_{식별자}_{문서-이름}.md`
- 식별자
  - 기본: 조사 기준 커밋의 짧은 해시 7자리 (예: `1102_a1b2c3d_handwriting-ocr-comparison.md`)
  - 특정 PR에 대한 보고서: `PR{번호 3자리}` (예: `1110_PR012_latency-measurement.md`)
  - 저장소가 아직 없어 커밋이 없을 때: `init` (예: `1030_init_{문서-이름}.md`)
- 테스트 데이터·계정 문서는 파일 하나를 계속 고쳐 쓴다. 이름의 날짜는 처음 만든 날로 고정한다. (예: `1115_a1b2c3d_test-data-and-accounts.md`)

## 작성 규칙

- **출처와 확인 날짜를 반드시 남긴다.** 출처 없는 주장은 「확인 안 됨」으로 표시한다.
- 조사 결과(사실)와 분석(해석)을 섞지 않는다.
- 테스트 데이터·계정
  - 테스트 데이터나 테스트 계정을 만들면 그 단계 뒤에 문서를 남긴다.
  - 모든 데이터 정보, 테스트할 수 있는 기능, 모든 테스트 계정의 역할·아이디·비밀번호·로그인 방식을 기록한다.
  - **테스트 전용 계정의 비밀번호만 적는다. 실제 비밀값(API 키, 토큰, 운영 계정 비밀번호, 개인 계정)은 절대 적지 않는다.**
  - 데이터가 바뀌면 새 문서를 만들지 않고 같은 문서를 고치고, 맨 아래 변경 기록에 날짜·내용·PR을 남긴다. 요청하지 않아도 언제든 최신 내용을 볼 수 있어야 한다.

## 문서 양식

아래를 그대로 복사해 쓴다. 해당 없는 절은 지우지 말고 「해당 없음」이라고 쓴다.

### 보고서

```markdown

|------|------|
| 작성일 | YYYY-MM-DD |
| 작성자 | {GitHub ID} |
| 기준 커밋 / PR | `{7자리}` 또는 PR{번호} |
| 요청자 | {이름 또는 GitHub ID} |

## 1. 요약

{결론을 세 줄 이내로 먼저 쓴다.}

## 2. 요청 내용

{무엇을 왜 조사해 달라고 했는지}

## 3. 조사 범위와 방법

- 방법: {문헌·문서 조사, 실험, 측정 방법과 환경}

## 4. 조사 결과

{사실만 쓴다. 각 항목 끝에 출처 번호 [1], [2]를 단다.}

## 5. 분석

{결과를 어떻게 해석하는지, 장단점, 위험}

## 6. 결론과 권고

- 결론: {…}
- 권고: {무엇을 하자고 하는지}

## 7. 후속 작업

- {이어서 할 일. 없으면 「해당 없음」}

## 8. 출처

| # | Source | URL / Path | Checked |
|---|--------|------------|---------|
| 1 | {제목·저자·기관} | {링크 또는 경로} | YYYY-MM-DD |
```

### 테스트 데이터·계정 문서

```markdown

|------|------|

| 작성자 | {GitHub ID} |
| 대상 환경 | {로컬 / 스테이징 등} |
| 데이터 생성 방법 | {스크립트 경로·명령 (예: `{명령}`)} |

> 테스트 전용 값만 적는다. 실제 비밀값(API 키, 토큰, 운영 계정 비밀번호)은 적지 않는다.

| Dataset | Location | Contents | Count | Notes |

{데이터를 처음 상태로 되돌리는 방법. 없으면 「해당 없음」}

## 5. 변경 기록

| Date | Change | PR |
```
