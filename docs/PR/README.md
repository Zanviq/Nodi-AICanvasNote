# PR

PR을 올릴 때마다 그 PR의 구체적인 설명과 관련 문서를 담는 폴더를 하나씩 만드는 공간이다. **PR 설명서가 없는 PR은 존재해서는 안 되며 이 규칙에는 예외가 없다.**

## 용도

- PR 설명서 (PR마다 1개, 필수)
- 셀프 리뷰 기록 (리뷰했을 때)
- 그 PR에만 필요한 추가 문서 (스크린샷 설명, 측정 결과 등)
- 여기에 두지 않는 것: 작업 설계(`docs/work/`), 설계 변경(`docs/design/`), 조사 보고서(`docs/report/`)

## 이름 규칙

| 대상 | 형식 | 예 |
|------|------|-----|
| PR 폴더 | `MMDD_PR{번호 3자리}_{작업-이름}/` | `0924_PR002_login-page/` |
| PR 설명서 | 폴더와 같은 이름 + `.md` | `0924_PR002_login-page/0924_PR002_login-page.md` |
| 리뷰 기록 | `MMDD_PR{번호 3자리}-REVIEW_{작업-이름}.md` | `0925_PR002-REVIEW_login-page.md` |
| 추가 문서 | `MMDD_PR{번호 3자리}_{작업-이름}-{내용}.md` | `0924_PR002_login-page-screenshots.md` |

- 폴더 날짜는 **PR을 처음 연 날**로 고정한다. 나중에 고쳐도 바꾸지 않는다.
- 리뷰 기록·추가 문서의 날짜는 그 문서를 쓴 날이다.
- PR 번호는 3자리로 맞추고 모자라면 앞을 0으로 채운다. 1000번부터는 그대로 쓴다.
- `{작업-이름}`은 브랜치 이름에서 접두어(`feat/` 등)를 뺀 부분을 쓴다.

## PR 절차

하나도 건너뛰지 않는다.

1. 작업 브랜치에서 **Draft PR**을 열어 번호를 받는다.
2. 곧바로 그 번호로 PR 폴더와 설명서를 만들어 같은 브랜치에 커밋하고 푸시한다.
3. GitHub PR 본문은 `.github/pull_request_template.md` 양식으로 요약하고 **설명서 경로를 반드시 넣는다.**
4. 아래 「Ready for review 전 체크리스트」를 모두 확인한 뒤에만 Ready for review로 바꾼다.
5. 병합한다. 1인 개발이므로 리뷰어 승인이 필요 없고, 작성자가 직접 병합하고 이슈를 닫을 수 있다.
   - AI는 사용자가 대화·PR 코멘트 등으로 그 PR(또는 병합까지 포함한 작업)의 병합을 지시했을 때만 병합한다. 지시가 없으면 PR을 열어 둔 채 보고한다.
   - 병합 직전에 설명서 6절 아래에 「6.1 승인 기록」을 추가해 커밋한다.
6. 병합한 작업 브랜치를 지운다.

원격 CI가 돌지 않으면 같은 검사를 로컬에서 돌리고, 무엇을 돌렸고 무엇을 생략했는지 리뷰 기록과 승인 기록에 그대로 적는다.

## Ready for review 전 체크리스트

- [ ] 설명서가 작업 브랜치에 커밋·푸시되어 있다.
- [ ] 설명서의 PR 링크·브랜치·작업 설계 경로가 실제와 같다.
- [ ] GitHub PR 본문에 설명서 경로가 있다.
- [ ] 작업 설계 문서(`docs/work/…`)의 진행 기록과 상태가 갱신됐다.
- [ ] 커밋이 작게 나뉘어 있다. (한 커밋 한 이유, 15파일/300줄 기준)
- [ ] 최신 `dev`가 반영되어 있고 충돌이 없다.

## 문서 양식

아래를 그대로 복사해 쓴다. 해당 없는 절은 지우지 말고 「해당 없음」이라고 쓴다.

### PR 설명서

```markdown
# PR{번호}: {PR 제목}

| 항목 | 내용 |
|------|------|
| 작성일 | YYYY-MM-DD |
| 작성자 | {GitHub ID} |
| 브랜치 | `{type}/{작업-이름}` → `dev` |
| PR 링크 | https://github.com/{owner}/{repo}/pull/{번호} |
| 관련 이슈 | #{번호} 또는 해당 없음 |
| 관련 설계 | `docs/design/…` (문서·절 이름, 결정 번호 D-XXX) |
| 작업 설계 경로 | `docs/work/{브랜치 이름}/MMDD_{문서-이름}.md` |

## 1. 목적

{이 PR이 왜 필요한지, 무엇을 해결하는지 쓴다.}

## 2. 변경 사항

| Area | File / Module | Change |
|------|---------------|--------|
| {영역} | `{경로}` | {무엇을 바꿨는지} |

## 3. 설계·결정 반영

- 따른 설계: {문서·절, 결정 번호}
- 설계와 다르게 한 부분과 이유: {없으면 「해당 없음」}

## 4. 디자인 영향

- {바뀐 화면·컴포넌트·토큰. DESIGN.md·디자인 시스템 문서 변경 여부}

## 5. 테스트

| Check | Command / Method | Result |
|-------|------------------|--------|
| typecheck | `{명령}` | {통과/실패} |
| lint | `{명령}` | {통과/실패/생략과 이유} |
| test | `{명령}` | {통과/실패/생략과 이유} |
| 수동 확인 | {기기·브라우저·절차} | {결과} |

## 6. 리뷰어가 볼 곳

- {먼저 봐야 할 파일·함수와 이유}

## 7. 배포·마이그레이션 메모

- {DB 마이그레이션, 환경 변수, 배포 순서. 없으면 「해당 없음」}

## 8. 관련 문서

- {리뷰 기록, 추가 문서, report 등 경로}
```

### 승인 기록

병합 직전에 PR 설명서 6절 바로 아래에 추가하고 커밋한다.

```markdown
### 6.1 승인 기록

| 항목 | 내용 |
|------|------|
| 병합 결정자 | {GitHub ID 또는 이름} |
| 날짜 | YYYY-MM-DD |
| 방법 | {직접 병합 / 대화에서 지시 / PR 코멘트 링크} |
| 병합 전 실제로 돌린 검사 | {명령과 결과. 원격 CI인지 로컬인지 명시} |
| 생략한 검사와 이유 | {없으면 「해당 없음」} |
```

### 리뷰 기록

```markdown
# PR{번호} 리뷰 기록: {PR 제목}

| 항목 | 내용 |
|------|------|
| 작성일 | YYYY-MM-DD |
| 리뷰어 | {GitHub ID} |
| PR 링크 | https://github.com/{owner}/{repo}/pull/{번호} |
| 기준 커밋 | `{7자리}` |

## 1. 확인한 범위

- 본 파일·커밋: {범위}
- 돌린 검사: {명령과 결과. 원격 CI인지 로컬인지 명시}
- 생략한 검사와 이유: {없으면 「해당 없음」}

## 2. 수정할 사항

| # | Severity | Location | Issue | Action | Status |
|---|----------|----------|-------|--------|--------|
| 1 | {blocker/major/minor/nit} | `{파일:줄}` | {내용} | {이 PR / 리뷰 수정 PR / 보류} | {열림/수정됨(PR번호)/보류} |

- 병합을 막는 문제(blocker)만 이 PR에서 고친다.
- 나머지는 이후 리뷰 수정 PR에서 고친 뒤 Status 열을 갱신한다.

## 3. 메모

- {그 밖에 남길 내용. 없으면 「해당 없음」}
```
