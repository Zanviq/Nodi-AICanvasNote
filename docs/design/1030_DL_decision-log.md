## 결정

### D-001. 선생님·학생 구조를 없애고 개인 노트 앱으로 바꾼다

| 항목 | 내용 |
|------|------|
| 상태 | 확정 |
| 날짜 | 2026-10-30 |
| 결정자 | 사용자 (요청 원문) |
| 관련 문서 | `docs/design/1030_v01_canvas-note/1030_v01_product-overview.md` §3.2 |

- **맥락**: Nodi는 선생님이 학급과 교과서를 만들고 학생이 캔버스에서 묻는 교실용 서비스였다. 논문용 프로그램은 이를 축소·개선한다.
- **결정**: 역할(선생님·학생·관리자)과 학급 개념을 없앤다. 사용자는 자기 노트만 쓴다.
- **이유**: 사용자 지시. 연구 대상은 손글씨 노트 안의 질문 경험이다.
- **고려한 대안**: 해당 없음
- **영향**: 학급·권한·콘솔 화면과 관련 API가 범위에서 빠진다.

- **맥락**: 펜으로 손글씨를 쓰는 경험이 핵심이다.
- **결정**: 펜을 쓰는 태블릿(iPad + Apple Pencil, 갤럭시 탭 + S펜)을 1차 대상으로 한다. 진짜 노트앱 수준의 필기감(압력, 기울기, 낮은 지연, 손바닥 무시)을 제공한다.

### D-003. AI 입력창 없이 손글씨 문장을 펜으로 두 번 톡 해서 묻는다

| 항목 | 내용 |
|------|------|
| 상태 | 확정 |
| 날짜 | 2026-10-30 |
| 결정자 | 사용자 (요청 원문) |
| 관련 문서 | `1030_v01_handwriting-question-recognition.md` §3 |

- **맥락**: 노트 앱이므로 대부분은 일반 필기다. 질문은 그 필기의 일부로 쓴다.
- **결정**: 텍스트 입력창을 두지 않는다. 사용자가 펜으로 특정 문장 위를 빠르게 두 번 톡 하면 그 문장을 골라 자동으로 인식하고 답을 받는다. 문장 범위를 찾는 알고리즘은 직접 설계한다.
- **이유**: 사용자 지시. 문장을 얼마나 잘 잘라 내는지가 관건이다.
- **고려한 대안**: 해당 없음
- **영향**: 제스처 판정, 문장 범위 추정, 인식, 필기와의 충돌 처리가 핵심 설계가 된다.

### D-008. 기술 스택: 태블릿 브라우저용 웹 앱(PWA) + Nodi 백엔드 재사용

| 항목 | 내용 |
|------|------|
| 상태 | 제안 |
| 날짜 | 2026-10-30 |
| 결정자 | AI 제안, 사용자 확인 대기 |
| 관련 문서 | `1030_v01_product-overview.md` §3.8, §4 · `CLAUDE.md` §2 |

- **맥락**: Nodi는 Next.js + FastAPI + PostgreSQL이고, 손글씨 인식은 Gemini, 답변은 Upstage `solar-pro3`를 썼다.
- **결정**: 프런트는 Next.js(App Router) + React + TypeScript로 만든 PWA, 필기는 Canvas 2D + Pointer Events + perfect-freehand로 그린다. 백엔드(FastAPI), DB(PostgreSQL), AI 호출부는 Nodi에서 가져와 줄인다.
- **이유**: iPad와 갤럭시 탭을 한 코드로 지원하고, 논문 일정 안에서 Nodi 자산을 재사용한다.
- **고려한 대안**: iPadOS 네이티브(Swift + PencilKit)는 필기감이 가장 좋지만 갤럭시 탭을 못 쓰고 Nodi 코드를 재사용할 수 없다. Flutter는 두 기기를 지원하지만 팀 경험과 Nodi 재사용 면에서 불리하다.
- **영향**: 웹에서 필기 지연을 줄이는 작업(예측 그리기, 저지연 캔버스)이 필요하다. 확정되면 `CLAUDE.md` §2의 「제안」 표시를 지운다.

### D-009. 문장 범위는 2단계(획 기하 후보 → 인식 후 경계 점수)로 찾는다

| 항목 | 내용 |
|------|------|
| 상태 | 제안 |
| 날짜 | 2026-10-30 |
| 결정자 | AI 제안, 사용자 확인 대기 |
| 관련 문서 | `1030_v01_handwriting-question-recognition.md` §3.6–3.8 |

- **맥락**: 손글씨 노트에는 마침표가 자주 빠지고, 문장이 줄 중간에서 시작하거나 여러 줄에 걸친다.
- **결정**: 1단계에서 획의 위치·크기·쓴 시간만으로 후보 줄 덩어리를 0.1초 안에 잡아 보여 주고, 2단계에서 그 덩어리만 글자로 읽은 뒤 문장 끝 신호(문장부호, 한국어 종결어미, 줄바꿈, 목록 기호, 쓴 시간 간격)를 점수로 합쳐 두 번 톡 한 자리가 들어 있는 문장 하나를 고른다.
- **이유**: 기하만으로는 줄 중간 경계를 못 찾고, 글자만으로는 줄 배치·쓴 순서 정보를 잃는다. 덩어리만 읽으면 인식 비용과 지연이 작다. 특징별 점수라서 논문에서 기여도를 따로 측정할 수 있다.
- **고려한 대안**: 같은 문서 §4.
- **영향**: 인식 엔진은 줄 단위 텍스트를 돌려줘야 한다.

### D-010. 두 번 톡 판정 조건: 펜 입력, 펜·연필 도구, 0.3초·3mm, 글자 위

| 항목 | 내용 |
|------|------|
| 상태 | 제안 |
| 날짜 | 2026-10-30 |
| 결정자 | AI 제안, 사용자 확인 대기 |
| 관련 문서 | `1030_v01_handwriting-question-recognition.md` §3.3, §3.13 |

- **맥락**: 마침표, 쌍점, 말줄임표 같은 점 필기와 질문 제스처가 겹친다.
- **결정**: 펜 입력(`pointerType === "pen"`)이고 도구가 펜이나 연필일 때만 판정한다. 각 톡은 0.18초 이하·1mm 이하 이동, 두 톡 사이는 0.3초 이하·3mm 이하, 두 톡 모두 같은 단어 획 위에 있어야 한다. 0.25초 안에 세 번째 톡이 오면 필기로 본다. 애매하면 필기로 남긴다.
- **이유**: 잘못 잡힌 질문은 취소 한 번이면 되지만, 사라진 필기는 되돌리기 어렵다.
- **고려한 대안**: 길게 누르기, 펜 버튼, Apple Pencil 더블탭(같은 문서 §4).
- **영향**: 첫 톡은 곧바로 점으로 그리고, 질문으로 판정되면 지운다.

### D-011. AI 글은 사용자 펜에 없는 전용 잉크색과 인쇄체로 쓴다

| 항목 | 내용 |
|------|------|
| 상태 | 제안 |
| 날짜 | 2026-10-30 |
| 결정자 | AI 제안, 사용자 확인 대기 |
| 관련 문서 | `1030_v01_design-system.md` §3.2, §3.3 |

- **맥락**: 내가 쓴 것과 AI가 쓴 것이 한 쪽에 섞인다.
- **결정**: AI 답은 손글씨 흉내를 내지 않고 인쇄체로 쓴다. AI 잉크색은 사용자 펜 색상표에서 뺀다. 색 말고도 표시(도장·쪽지·번호)를 하나 더 둔다.
- **이유**: 출처가 한눈에 보여야 다시 읽을 때 믿을 수 있다. 색만으로 구분하면 색각 이상 사용자가 놓친다.
- **고려한 대안**: 손글씨 글꼴로 답 쓰기는 내 글씨와 헷갈려서 버렸다.
- **영향**: 디자인 토큰 `--ink-ai`는 펜 색상표에 넣지 않는다.

### D-012. 답을 넣으면 아래 필기를 줄 단위로 밀고, 넘치면 그 쪽에 종이를 이어 붙인다

| 항목 | 내용 |
|------|------|
| 상태 | 제안 |
| 날짜 | 2026-10-30 |
| 결정자 | AI 제안, 사용자 확인 대기 |
| 관련 문서 | `1030_v01_handwriting-question-recognition.md` §3.11 |

- **맥락**: 질문 아래에 이미 필기가 있는 경우가 대부분이다.
- **결정**: 답이 들어갈 줄 수만큼 질문 아래의 모든 필기와 답을 줄 단위로 아래로 민다. 쪽 아래로 넘치면 다음 쪽으로 흘려 보내지 않고 그 쪽 아래에 종이를 이어 붙여(쪽 높이를 줄 단위로 늘려) 담는다.
- **이유**: 손글씨와 그림은 다음 쪽으로 쪼개면 망가진다. 줄 단위 이동이면 괘선과 글씨의 관계가 유지된다.
- **고려한 대안**: 답을 필기 위에 겹쳐 띄우기(가림), 옆 여백에 쓰기(D-004와 어긋남), 다음 쪽으로 흘리기(그림이 잘림).
- **영향**: 쪽 높이가 쪽마다 달라질 수 있다. 내보내기(PDF)에서 이어 붙인 쪽 처리가 필요하다.

| 관련 문서 | `1030_v01_handwriting-question-recognition.md` §3.12 |

- **맥락**: 이어 질문 칸에 쓰다가 잠깐 멈추는 일이 잦다.
- **결정**: 칸에 쓴 글 전체가 질문이다. 사용자가 칸 안의 글씨를 두 번 톡 하거나 「묻기」를 누르면 보낸다. 쓰기를 멈췄다고 저절로 보내지 않는다.
- **이유**: 첫 질문과 같은 제스처로 배우기 쉽고, 생각하는 중에 반쯤 쓴 질문이 나가지 않는다.
- **고려한 대안**: 일정 시간 멈추면 자동 전송(설정으로 켤 수 있게 할지는 남은 질문).
- **영향**: 칸 안에서는 문장 범위 추정을 하지 않는다.

### D-014. 시각 방향은 시안 A·B·C 중에서 고른다. 고르기 전까지 DESIGN.md 값은 시안 A 기준

### D-016. 종이 종류(괘선·모눈·무지)는 노트마다 고른다

| 항목 | 내용 |
|------|------|
| 상태 | 제안 |
| 날짜 | 2026-10-30 |
| 결정자 | AI 제안, 사용자 확인 대기 |
| 관련 문서 | `1030_v01_design-system.md` §3.5 · `1030_v01_handwriting-question-recognition.md` §3.5 |

- **맥락**: 과목과 사람마다 쓰는 종이가 다르고, 세 시안이 각각 다른 종이를 보여 준다.
- **결정**: 노트를 만들 때 괘선, 모눈, 무지 중 하나를 고른다. 줄 찾기는 괘선·모눈이면 줄 간격을 쓰고, 무지면 획을 묶어 줄을 추정한다.
- **이유**: 실제 노트앱의 기본 기능이고, 논문에서 종이 종류별 범위 추정 정확도를 비교할 수 있다.
- **고려한 대안**: 괘선 하나만 지원(구현은 쉽지만 무지에서의 알고리즘을 검증할 수 없다).
- **영향**: 종이 템플릿 토큰과 줄 구성 알고리즘의 두 경로.
